# 门户「发送瞬间整屏重建」修复方案 (2026-11-10)

## 0. 一句话

给门户的消息行换一个**稳定身份** (修法 1), 再让 `sameHead` 允许**只重建末尾那一两行** (修法 2)。
两条都不动 dsh、不动 jsonl、不动球的渲染。

## 1. 现象与读数

在门户点发送的那一瞬间, 消息流会整块重建 (`resetFlow`), 观感是"整屏闪一下 / 重排"。
现场可直接读的计数器就在代码里: `window.__LW_PORTAL_STATS__.rebuilds` / `.appends`
(`presets/luwi-portal/lib/client.js` 955-957)。发一条消息, `rebuilds` 涨 1~2 就对了。

### 1.1 现状链路 (2026-11-10 读数)

| 步骤 | 代码位置 | 行为 |
| :-- | :-- | :-- |
| 发送 | `send()` 3146 | `sending=true`、输入框清空、`portalBind`、`beginSubmission`、`session.prompt` |
| 取节点 | `nodesOf` 1581 | user / steering 节点 → `kept.push({who, time, text, attach, hasImage})` |
| 签名 | `flowSignature` 2201 | 逐条拼 `who/time/text/…` |
| 身份 | `itemKey` 2217 | `who + seq + time + text + …`, 而 `seq` 在 kept 里**根本没塞** (= undefined) |
| 前缀比较 | `sameHead` 2417 | 与 `flowRows` 逐条比 key, 有一条不等就 false |
| 重建 | 2426-2429 | `!sameHead` → `resetFlow()` + `rebuilds += 1` + 强制贴底 |

### 1.2 为什么发送必然重建一次

`itemKey` 把 `time` 当身份, 而这几处会同时改掉末尾行的 `time`:

1. 新 user 行进入流, 最后一行从"上一轮那条"变成"这一条";
2. 上一轮若有兜底正文行, `fallbackAt` 在新一轮开始时被重置 (1638), 兜底行的 `time` 跟着变;
3. 「说完了」那行 (`doneNoteAt`) 的时间也会变。**2026-11-10 晚这行已经删了** (主人: "去掉那 3 个字") ——
   宿主 turn end 会补一行 `lw_say`, 门户不再需要这条兜底安静行; 下面凡提它的, 都只当当时的分析留档

任何一条落在**非末尾位置**时, 前缀比较到它就失败 → 整块重建。稳定性问题不在"渲染太慢",
而在**身份不稳定**。

## 2. 修法 1: 稳定身份

### 2.1 数据在哪

dsh 快照的 user 节点 (`ui-chat` 的 `message.ts` 108-134) 自带三个稳定字段:

| 字段 | 含义 | 稳定性 |
| :-- | :-- | :-- |
| `node.messageId` | durable 消息 id | 落盘后稳定 |
| `node.source.rpcId` | 提示词的关联身份 (Host 把它回显为 durable `user/message` 的 `rpcId`) | 回显与落盘**同一个值** |
| `node.seq` | 会话日志序号 | 落盘后稳定 |

门户的 `kept.push` 目前三个都没带。**修法 1 = 把它们带上, 并用它做身份。**

### 2.2 改法

- `kept` 的 user / steering 行增加 `id`: 取 `node.messageId ?? node.source?.rpcId ?? (node.seq 有值时的 'seq:' + seq)`;
- `itemKey` 的 user 行改为 `who + id + …` (不再用 `time`; `time` 只参与 30 分钟分段与排序);
- `flowSignature` 同步改用 `id` —— 签名与身份必须是同一套键, 否则"签名说不重要、身份说变了";
- 兜底正文行的身份改成**它所依附的那条 user 的 id** (`fallbackId`), 不再用 `fallbackAt` 时间;
- 「说完了」那行的身份用触发它的那一轮 user id, 不用 `Date.now()`。

### 2.3 验收

发送一条消息: `rebuilds` **不增**, `appends` 增 1。落盘前后各读一次, 稳定身份让两次是同一个 key。

## 3. 修法 2: 允许只重建末尾

修法 1 只能消除"user 行身份抖动"。附件解析、兜底行、note 行仍可能在就地变化时改 key, 所以
还要给 `sameHead` 一条"尾部替换"的退路, 不必整块重建。

### 3.1 判据

求 `flowRows` 与 `plan` 的最长公共前缀长度 `L`:

| 情况 | 处理 |
| :-- | :-- |
| `L === plan.length` | 不动 (签名闸已挡, 走不到这里) |
| `L === plan.length - 1` | **只替换最后一行**: `flowRows[L].el.replaceWith(新节点)`, `appends += 1` |
| `L >= plan.length - 2` | 重建尾部 2 行 (兜底行 + 新行这一对常见的组合) |
| 其它 | `resetFlow()` (真正的前缀变化, 例如换场 / 删消息) |

### 3.2 实现要点

- `flowWorking` (末尾「正在做…」) 不是 plan 里的一行, 替换尾部时它必须保持在最后;
- `sep` (30 分钟分段药丸) 也是 plan 里的一行, 同样参与前缀比较, 天然被上面的规则覆盖;
- 替换后 `flowRows` 的 `key` 必须同步更新, 否则下一次比较会用旧 key;
- 只替换 DOM, 不重算滚动的意图: `follow` 保持原判据, 替换完照常 `stickFlow()`。

## 4. 判据

1. **计数**: 连续发 5 条 (含一条带图), `rebuilds` 增量为 0; `appends` 增 5 (+ 附件解析那次尾部替换)。
2. **真机观感**: 发送瞬间对话框不闪、不重排, 只有新气泡出现与滚动贴底。
3. **回归**: 换会话 / 开新对话 / 收起再张 / 30 分钟分段 —— `rebuilds` 该涨的仍要涨 (换场本来就必须重建)。
4. **单元口径**: `itemKey` 对同一节点在"缺一相"两拍之间返回同一个串 (可把这两个函数抽出来做真值表,
   与 `flowSignature` 一起测)。

## 5. 改动面

| 文件 | 改动 |
| :-- | :-- |
| `presets/luwi-portal/lib/client.js` | `kept.push` 补 `id`; `itemKey` / `flowSignature` 改用 `id`; `sameHead` 改为前缀长度 + 尾部替换; 兜底/note 行的身份改挂在 user id 上 |
| 无 | dsh、宿主、球、jsonl 一律不动 |

## 6. 风险与回退

| 风险 | 处置 |
| :-- | :-- |
| `messageId` / `rpcId` 在某些节点缺失 | 三级回退: `messageId` → `source.rpcId` → `seq:N` → 最后才退 `time` (退到 time 就等于今天的行为, 不会更糟) |
| 尾部替换把「正在做…」挤掉 | 替换只针对 plan 行, `flowWorking` 单独 append 在最后 |
| 身份重复 (同一 id 出现在两行) | 比较时按 `id + 位置` 拼 key, 位置进 key 可避免撞 (与修法 1 的"id 优先"不冲突) |
| 真的需要整块重建的场合被省掉 | 只放行"末尾 1~2 行"的变化, 其余仍走 `resetFlow` |

回退: 两处都只改客户端 JS, 关掉门户 (`localStorage['dsh.luwi.portal']='off'`) 即完全绕开。

## 7. 落地顺序

1. 修法 1 (稳定身份) —— 先做, 因为它是"根";
2. 修法 2 (尾部替换) —— 再兜住剩余的就地变化;
3. 用 `__LW_PORTAL_STATS__` 做前后读数对比, 真机 A 录一组 (发送 / 带附件发送 / 换场) 收尾。

## 8. 实施前需确认的一行读数

门户画的是 `snapshot.legacy.nodes`。**pendingSubmissions 是否也进 legacy.nodes** 这一点要在实施前
用一行 console 确认 (`[luwi-portal] nodes=…` 那条已经在打)。若回显不进 legacy.nodes, 说明"发送中"
那一拍本来就没画, 修法 1 的收益就是把"新行出现"变成纯追加; 若进, 则 `rpcId` 让回显与落盘共用同一身份,
收益更大 (两次变化合成一次)。

### 9.1 落地了什么

替换后 `flowRows` 的 key 同步更新、滚动仍由 `follow` + `stickFlow()` 管 (尾部替换不改贴底判据)。
